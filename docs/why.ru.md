# Зачем ironharness

На странице — какую проблему решает ironharness, как попробовать его за
десять минут без железа и какой инструмент брать под какую ситуацию.

Команды установки и полный список инструментов — в [README](../README.ru.md).
Версия для агента (установка, карта тулов, правила работы) —
[`skills/ironharness/SKILL.md`](../skills/ironharness/SKILL.md).

## Какую проблему это решает

LLM-агент, работающий с реальным железом, обычно делает это голым pyserial'ом
в шелл-цикле. Типичные отказы:

- агент открыл порт и вечно висит на чтении — ни таймаута, ни дедлайна;
- вывод, пришедший между двумя вызовами инструментов, пропал;
- прошил или стёр плату — и никакой записи, кто, когда и что вернулось;
- упавшая сессия не оставила после себя ничего: следующая начинает с нуля и
  заново всё выясняет перебором;
- «получилось» недоказуемо — код возврата был 0.

ironharness встаёт между агентом и устройством и добавляет недостающие
ограничения: MCP-сервер (33 инструмента), где каждая операция пишется в
JSONL-журнал, транспорты ограничены дедлайнами и квотами, деструктивные
действия закрыты явными гейтами с opt-in, а доменные ошибки приходят
читаемым текстом с подсказкой следующего шага вместо стектрейса.

[Ops-демо](https://cezman.github.io/ironharness/ops-demo.html) делает одну
и ту же работу дважды на живой плате: стереть ESP32 и записать обратно
метеостанцию. Первый раз — голым esptool с самописным скриптингом поверх
pyserial, второй — через MCP-инструменты ironharness; журнал — протокол
аудита.

## Десять минут без железа

1. **Подключите сервер к любому MCP-клиенту** (Claude Code, Claude Desktop,
   Cursor, Codex, OpenCode…):

   ```json
   {
     "mcpServers": {
       "ironharness": {
         "command": "uvx",
         "args": ["--from", "ironharness", "ironharness-mcp"]
       }
     }
   }
   ```

2. **Попросите агента: «покажи мои COM-порты»**. Он вызовет `serial_list`, и
   вы получите порты с USB-идентификацией (VID/PID, номер COM-порта,
   описание). Плата не нужна — пустой список тоже нормальный ответ.

3. **Попросите агента: «открой loop://, напиши hello и прочитай обратно»**.
   `loop://` — виртуальный порт, встроенный в pyserial: всё записанное
   возвращается сразу. Это прогоняет цепочку открыть → писать → читать →
   закрыть без железа и без риска.

4. **Посмотрите в журнал:**

   ```
   type %USERPROFILE%\.ironharness\journal.jsonl    :: Windows
   cat ~/.ironharness/journal.jsonl                 # Linux / macOS
   ```

   Все операции из шагов 2–3 там: что открывалось, что писалось, что
   вернулось, что было отказано. По журналу агент, человек или скрипт
   восстановят, что произошло, даже после падения. Операция без записи в
   журнале считается не выполненной.

5. **С платой:** воткните её и спросите: *«на каком порту моя плата с
   CH340? Открой его и покажи, что она пишет»*. Агент сопоставит порт по
   VID:PID (CH340 = `1a86:7523`), откроет его (напрямую или через
   `by-serial:`) и дождётся загрузочного баннера, прежде чем писать.
   Открытие USB-UART порта может дёрнуть плату в перезагрузку, а команды,
   вписанные в полузагруженный REPL, съедаются.

6. **Опционально:** положите
   [`skills/ironharness/SKILL.md`](../skills/ironharness/SKILL.md) в
   каталог скиллов вашего агента. Там карта тулов и практические заметки:
   paste-режим для многострочного MicroPython-кода, почему дедлайны нельзя
   отключать, журнал как память агента.

[Demo-GIF](demo.gif) показывает сценарий «стереть и записать заново» на
живой плате; [board.jpg](board.jpg) — сам стенд.

## Карта модулей

`io-core` (он же PyPI-пакет `ironharness`; MCP-сервер) — слой небольших модулей:

| Модуль | Что даёт |
|---|---|
| `session.py` | `Session` — именованные транспорты + файловая песочница + один журнал; то, во что завёрнуты MCP-инструменты. `session_status` — самопроверка после любой потери контекста. |
| `serial_transport.py`, `serial_reader.py`, `mprepl.py` | pyserial-поверхность (только локальные порты, сетевые URL отказываются), фоновый читатель (вывод устройства между вызовами буферизуется, а не теряется), передача файлов на плату MicroPython и обратно через raw REPL. |
| `modbus_transport.py`, `modbus_sim.py` | Modbus TCP-клиент (FC3/6/16) и внутрипроцессный симулятор для офлайн-работы. |
| `mqtt_transport.py`, `mqtt_sim.py` | MQTT 3.1.1-клиент (открытый TCP без TLS — задокументировано, только для стенда) и минимальный внутрипроцессный брокер. |
| `esp_flash.py` | обёртка над esptool: офлайн-разбор образов прошивки, прошивка/стирание за гейтом `IRONHARNESS_ALLOW_REAL_FLASH=1`. |
| `file_sandbox.py` | файловый транспорт, замкнутый на свой корень, с квотами. |
| `journal.py` | JSONL-журнал: ротация по размеру, sidecar-лок — безопасно при записи из нескольких процессов. |
| `replay.py` | реплеер: восстановление сессии из её журнала. |
| `limits.py` | `DeadlineTransport`, `RateLimitedTransport` — дедлайны и квоты вокруг любого транспорта. |
| `verify.py` | `expect_read`, `write_and_expect` — проверить, что эффект произошёл, а не только что вызов вернулся. |
| `policy.py` | управляемые оператором списки доступа: `IRONHARNESS_ALLOWED_HOSTS`, `IRONHARNESS_ENABLED_KINDS`; каждый отказ журналируется. |
| `faults.py` | `FaultyTransport` — скриптованные обрывы, задержки, порча битов, потеря байтов поверх любого транспорта. |
| `errors.py` | типы доменных ошибок; агент получает их читаемым текстом с подсказкой следующего шага — таймаут советует закрыть и переоткрыть порт, отказ открытия отсылает к белому списку портов. |
| `mcp_server.py` | 33 инструмента поверх stdio. |

Модель безопасности в пяти строках:

1. **Журналируется всё** — операция без записи в журнале не выполнялась.
2. **Файлы живут только внутри песочницы**, на всё — квоты.
3. **Везде дедлайны и байтовые капы** — зависшее устройство не может
   завесить агента, а флуд не может раздуть его контекст.
4. **Деструктивное — за гейтом**: прошивка/стирание требуют extra `[flash]`
   и opt-in переменной окружения; прогоны бенча на живой плате требуют
   `IRONBENCH_REAL_PORT` и `--allow-real`, и `main.py` платы бэкапится до
   любой очистки.
5. **Сетью управляет оператор**: serial — белый список локальных портов,
   цели Modbus/MQTT можно запереть списком хостов.

Расширение: новый транспорт — «реализуй примитив, заверни в дедлайн +
рейт-лимит + политику, журналируй каждую операцию, выставь через сервер».
Задачи бенчмарка — обычный YAML в `src/ironbench/tasks/`: задача объявляет
прошивку, детектор (какое наблюдаемое поведение считается PASS) и
опциональные заметки эксперта.

## Рецепты: ситуация → инструмент

| Ситуация | Что брать | Где |
|---|---|---|
| Несколько USB-UART переходников, номера портов плавают при перетыкании | `serial_list` → сопоставить VID:PID; `serial_wait` блокируется до появления вашей платы; открыть через `by-serial:<sn>` | MCP-инструменты |
| Устройство печатает между вызовами, и вывод теряется | фоновый читатель: `serial_reader_start`, затем `serial_tail` / `serial_read_until` | MCP-инструменты |
| Посмотреть, что печатает плата, с ограничением (boot-лог, болтовня, тишина) | `serial_monitor`: капы max_bytes/max_seconds, quiet-окно, stop-паттерн, дамп в песочницу | MCP-инструменты |
| Плата зависла, нужна чистая попытка | `serial_reset` (RTS-импульс) | MCP-инструменты |
| Залить файл на плату / спасти её `main.py` | `serial_put` / `serial_get` (raw REPL; сначала бэкап) | MCP-инструменты |
| Прошить или стереть ESP32 | `esp_image_info` (офлайн-разбор) → `esp_flash` / `esp_erase`, отказ без `IRONHARNESS_ALLOW_REAL_FLASH=1` | MCP-инструменты + `ironharness[flash]` |
| Нужен фейковый девайс для разработки | `ModbusSimServer`, `python -m io_core.mqtt_sim` (из клона репозитория), порт `loop://` | `src/io_core/modbus_sim.py`, `src/io_core/mqtt_sim.py` |
| Нужна ненадёжная линия для resilience-тестов | `FaultyTransport`: скриптованные обрывы, задержки, порча | `src/io_core/faults.py` |
| Поговорить по Modbus или MQTT | `modbus_open/read/write/close`, `mqtt_open/publish/subscribe/read/close`; запереть адреса через `IRONHARNESS_ALLOWED_HOSTS` | MCP-инструменты |
| «Что именно сделал агент?» | читать журнал; воспроизвести сессию реплеером | `src/io_core/journal.py`, `src/io_core/replay.py`, `src/ironbench/journal_view.py` |
| Агент должен *доказать*, что эффект произошёл | `expect_read`, `write_and_expect` | `src/io_core/verify.py` |
| Безудержные записи или бесконечные переподключения | дедлайны и капы уже вокруг каждого транспорта; целые виды транспортов отключаются через `IRONHARNESS_ENABLED_KINDS` | `src/io_core/limits.py`, `src/io_core/policy.py` |
| Проверить, отвечает ли сенсор на шине I2C | эталонный паттерн: золотая задача `bus-diagnose` (скан шины, отчёт о пропавших, деградация без падения) | `src/ironbench/tasks/` |
| Прочитать сенсор без библиотек на плате | `bme-read` (BME280 прямо по даташиту), `cross-sensor` (BME280 + DS18B20 с перекрёстной проверкой) | `src/ironbench/tasks/` |
| Отладить развёрнутую прошивку, которая ведёт себя плохо | класс задач `debug-*`: баг лежит внутри задачи, PASS = фикс удовлетворяет спецификации | `src/ironbench/tasks/` |
| Измерить, что модель реально умеет на прошивках | `ironbench solve` → `ironbench report` (pass@k, профили по классам) | README → ironbench |

## Бенчмарк (ironbench)

Если цель — измерять агентов, а не управлять железом: ironbench везёт каталог
золотых прошивочных задач (`python -m ironbench.cli list`), у каждой — класс
(io / data / protocol / fsm / control / resilience / debug) и уровень от 1 до
5, пять мишеней: Wokwi ESP32/MicroPython, MicroPython unix-порт, Renode,
замкнутая симуляция «объект + регулятор» и живая плата. Задача считается
решённой, только когда *раннер* проверил наблюдаемое поведение прошивки
(ответы serial-протокола, тайминги пинов, показания сенсоров), а не «строки
похожи на правду». Числа, архивные поколения с сырыми данными по попыткам и
кейс-стади находятся на [gh-pages](https://cezman.github.io/ironharness/).
